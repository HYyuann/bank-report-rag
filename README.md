## 数据来源

巨潮资讯网（cninfo.com.cn）公开公告查询接口。摸索出的几个关键点，避免以后重复踩坑：

1. `stock` 参数**必须**写成 `"代码,orgId"`，只传代码会返回 0 条。orgId 通过
   `POST /new/information/topSearch/detailOfQuery`（表单参数 `keyWord=<代码>`）获取，
   取 `keyBoardList[]` 中 `category == "A股"` 的那一项的 `orgId`。
2. `column` 必须与上市地一致：沪市 `sse`，深市 `szse`。
3. `category=category_bndbg_szsh` 即「半年度报告」，**沪深通用**，一个值即可。
4. 每家在 2026 全年区间内正好返回 2 条：**正文 + 摘要**。各家标题格式不统一
   （「招商银行股份有限公司2026年半年度报告」vs「工商银行2026半年度报告」，
   有的不带「年/度」），因此过滤规则为「必须含『半年度报告』或『半年报』」
   并排除 `摘要/英文/更正/补充/提示性/公告/修订` 等词，再按日期 + 体积取最大。
5. PDF 实际地址为 `http://static.cninfo.com.cn/` + 公告的 `adjunctUrl`。

12 家银行的 orgId 已实测取得，作为接口临时故障时的兜底值内置在脚本的
`ORG_ID_FALLBACK` 中。

## 已知问题

### 招商银行半年报正文为繁体

招商银行 A+H 两地上市，其在巨潮 A 股「半年度报告」类目下披露的正文
（`600036_招商银行_2026H1.pdf`）**全篇为繁体中文**——封面写作
「2026 年半年度報告 A 股股票代碼：600036」。经核查该股 2026 半年报类目下
只有这一份正文 + 一份摘要，没有对应的简体版本，因此**保留使用**该文件。

**处理方式**：在第二步文本提取环节统一做繁 → 简转换，使用 `zhconv`
（已装进项目 `.venv`）。

```python
import zhconv
text = zhconv.convert(text, "zh-cn")   # 淨利息收入 -> 净利息收入
```

**原因**：语料中混入繁体将同时拖累 embedding 与 BM25 的中文匹配效果——
繁体字形与简体字形的 token 不一致，同一概念无法命中；BM25 尤其严重，
「淨利息收入」查不到「净利息收入」。统一转简体后语料才是同分布的。

### 向量模型没用课件推荐的 Qwen3-Embedding-0.6B

**课件推荐 `Qwen/Qwen3-Embedding-0.6B`（1024 维）**，本项目实际用的是
**`BAAI/bge-small-zh-v1.5`（512 维）**，原因是本机无 GPU、Qwen3 全量编码需 2~4 小时，
要先把全流程跑通。

排查过程（这一步值得记，因为它不是简单的「模型大所以慢」）：

1. 第一版直接跑，实测 **22 秒/块，2553 块要 11 小时**。
2. 先怀疑注意力实现，eager 换 sdpa 只快 1.4 倍（23 → 16 秒/块），不是主因。
3. 打印权重 dtype 才发现根因：**Qwen3-Embedding 仓库里存的是 bfloat16**，
   `SentenceTransformer` 默认照单全收，而本机 CPU 是 Alder Lake、
   **没有 AVX512-BF16**，torch 只能走慢速兜底——吞吐被钉在 59 token/s。
4. 显式转 float32 后 **261 token/s**，快 4.4 倍，但全量仍需 2~4 小时。

```python
SentenceTransformer(name, device="cpu", model_kwargs={"dtype": torch.float32})
```

顺带扫出来的配置（8 块样本，取两遍最快值；这台机器上）：

| 配置 | 秒/块 | 2553 块 |
|---|---|---|
| bge-small-zh fp32 batch=16 | **0.08** | **约 4 分钟** |
| Qwen3 fp32 batch=4 | 3.2 | 2.3 小时 |
| Qwen3 bf16 batch=4 | 15.8 | 11.2 小时 |
| Qwen3 fp32 batch=8 | 6.9 | 4.9 小时 |
| Qwen3 fp32 + int8 动态量化 batch=16 | 7.3 | 5.2 小时 |

即：**Qwen3 在这台机器上 batch 要小（4），int8 动态量化反而更慢**。
换 bge-small-zh 后快约 40 倍，代价见下一条。

如果之后要换回课件指定的 1024 维 Qwen3，把 `build_index.py` 里的
`MODEL_NAME` / `DIM` 改回去即可——断点指纹里带了模型名，换模型会自动作废旧断点，
不会拿 512 维的旧向量拼新索引。

### bge-small-zh-v1.5 上下文只有 512 token，长块会被截断

`bge-small-zh-v1.5` 的位置编码上限是 512 token，而本批块平均约 1,066 token
（中位数，最长 2,203）——**2,553 块里有 2,548 块（99.8%）会被截断**，
平均只有前 48% 进入向量。

**这是为跑通全流程接受的已知取舍**，应对方式是两路互补：

- **向量路**：入库文本带了 `《{简称}2026年半年度报告 · {章节}》` 抬头，
  被截断时保留的是「章节开头」——恰好是结论、总额、小计所在的位置。
- **BM25 路**：jieba 分词 + `BM25Okapi` 覆盖**全文不截断**，块尾部的内容
  （尤其是长表格的后半段）只在这条路上能被召回。

`index_info.json` 里记了 `max_seq_length` / `truncated_chunks` / `token_len_median`，
每次建索引都会重新统计并打印，换模型或改切块参数后能立刻看出截断比例的变化。

### BM25 单独用时分不清是哪家银行

三个自检问题里，**BM25 的首条命中三题全部是错公司**。例如问「招商银行 2026 年上半年
净息差是多少」，BM25 首条给的是**平安银行** p47（「本集团净息差 1.80%」）。

不是分词问题，是排序问题：

1. 每家 200 多块的入库文本都带抬头 `《{简称}2026年半年度报告 · {章节}》`，
   于是「招商银行」在 2,553 块里出现在约 240 块中——**IDF 拉不开差距**，
   它几乎不能把候选集收窄到目标公司。
2. `BM25Okapi` 默认 `b=0.75`，长度归一化很重。本批块平均 666 个 jieba 词，
   而「净息差」在短块（如平安 p47 那样的一小节）里词频密度高，
   长块的得分被长度压下去，于是**密集提到关键词的短块压过了目标公司的分析页**。

**这是第四步要做混合检索 + 公司元数据过滤的直接理由**，不是 bug，要在评测里量化。
向量路在同一批问题上表现相反：三题里两题首条就命中正确公司和指标
（招商银行净息差 → 管讨 p15-16；工商银行手续费及佣金 → 财务报告 p23-25，
原文即「上半年，手续费及佣金收入 765.91 亿元，同比增加 24.29 亿元，增长 3.3%」）。

## 第四步：混合检索怎么做的

针对上面两条问题各下一味药。

**RRF 融合**（`rag.py`）。向量和 BM25 各取 top-10，按名次倒数求和：

```
score(d) = Σ_route  1 / (60 + rank_route(d))        合并去重后取前 6 条
```

只用名次、不用原始分数，是因为余弦相似度（0~1）和 BM25 分数（0~20+）
不同量纲，硬加权需要先调权重，而权重只能靠拍脑袋或拿测试集刷——
RRF 没有超参可调（`k=60` 是文献惯例值），在这个规模上更省事也更稳。

**公司过滤**（`rag.py` 的 `detect_company` + 两轮检索）。问题里出现哪家银行的
简称或代码，就先在该公司的子集里检索一轮（**限定轮**），同时照跑一轮全局
检索做**兜底轮**，最后限定轮结果在前、兜底轮补足去重。两轮都留的理由是：
简称识别可能出错，只跑限定轮的话一旦认错公司，正确答案会被彻底挡在门外。
代码（`600036`）优先于简称匹配，简称按长度从长到短匹配，避免「中国银行」
先被短别名抢走。

实测效果（`ask.py --retrieval-only`，召回 6 条）：

| | 第三步：BM25 单独用 | 第四步：混合 + 公司过滤 |
|---|---|---|
| Q1 招商银行净息差 | 首条是**平安银行** p47 | 6 条**全是招商银行** |
| Q3 工商银行手续费 | 首条不是工商银行 | 6 条**全是工商银行**，且答案页 p23-25 升到第 1 |

Q3 的答案页（`601398_0014`，原文即「上半年，手续费及佣金收入 765.91 亿元，
同比增加 24.29 亿元，增长 3.3%」）在两路里都是高分：向量第 1、BM25 第 4，
融合后第 1（RRF 0.03202 = 1/61 + 1/64），是个干净的「两路都认」的例子。

**但真正修好「串公司」的是公司过滤，不是 RRF。** 这一点单独做过消融
（Q1，逐个模式关掉公司过滤，看 6 条里有几条是招商银行、首条对不对）：

| 配置 | 6 条里的招商银行 | 首条 | 判定 |
|---|---|---|---|
| 只用向量，无过滤 | 6/6 | 招商银行 p8-9 | ✅ 首条正确 |
| 只用 BM25，无过滤 | 1/6 | **平安银行 p47** | ❌ 串公司 |
| 混合（RRF），无过滤 | 3/6 | **平安银行 p47** | ❌ **比只用向量还差** |
| 混合 + 公司过滤 | 6/6 | 招商银行 p237 | ✅ 首条正确 |

第三行值得单独说：RRF **不但没修好，还比单用向量更差**。原因是平安 p47 在
BM25 里是第 1，向量里也排到第 8——两路都有分，RRF 就把它顶到了第一
（0.03110 = 1/61 + 1/68），反而把向量单独用时的正确首条挤到第 2。

**结论：RRF 解决的是「互补召回」（把 BM25 独有的块捞回来），公司过滤解决的
才是「串公司」。两者管的是不同的事，缺一不可**——这也解释了为什么只上混合检索
并不够。截图见 `shots/q1_只用向量_无公司过滤.png` 等三张。

**冷启动开销**：首次检索约 46 秒，其中绝大部分是 `SentenceTransformer` 加载
权重 + 第一次前向；预热之后每次检索 20~30 毫秒。页面里用 `@st.cache_resource`
把这一笔开销挡在启动阶段（`app.py` 的 `get_retriever` 会主动碰一下 `r.model`）。

### 口径/同义词扩展：把「净息差」接到报表用词上

问「招商银行 2026 年上半年**净息差**是多少」，而招商银行报表里从头到尾写的是
**净利息收益率**和**净利差**——字面上一个词都对不上。这一层是专门修这个的。

做法（`rag.py` 的 `SYNONYMS` + `expand_query`）：问题里命中指标名就**追加**
同义词（不是替换——原词往往是块里词频最高的，换掉会丢分），然后把扩好的查询
同时喂给向量和 BM25 两路。**并且把这个对应关系一并写进提示词**：

```
【口径说明】检索时已按本项目的指标口径对照表，把问题中的指标一并按
「净利息收益率、净利差、NIM」检索。若材料中出现这些表述，即视为同一指标的
披露口径，可以直接用其数值回答，出处照抄材料里的用词。
```

**这一步不能省。** 只扩检索、不告诉模型的话，它照样拒答——因为它的判断依据是
「材料里没有『净息差』这个词」，而这跟检索捞回了什么无关。把口径对应关系作为
**材料的一部分**给它，而不是指望它拿常识去等同，才不违反 system prompt 里
「不得使用材料以外的知识」。

同一问题的开/关对比（`ask.py --no-expand` vs 默认）：

| | 扩展**关** | 扩展**开** |
|---|---|---|
| 实际检索词 | 招商银行 2026 年上半年净息差是多少？ | 同上 ＋（净利息收益率、净利差、NIM） |
| 融合后第 1 | **`600036_0233` 财务报告 p237（债券股息表，无关）** | `600036_0006` 公司简介与主要财务指标 p8-9 ✅ |
| 融合后第 2 | `600036_0006` p8-9（向量#1，BM25 落榜） | `600036_0013` 管讨 p15-16 ✅ |
| 含净利息收益率的块 | 只有 p15-16 一条，且卡在第 6 | p8-9 / p15-16 / p15 三条，占前 3 |
| 最终答案 | **「检索到的材料无法回答」**，只列了净利差 1.77%、净利息收益率 1.83% 作参考 | **「净利息收益率为 1.83%」**，带 3 处出处 |

两路的分数变化也很干净：BM25 上 p8-9 从**落榜**升到 **#1（33.18）**、p15-16 到
**#2（30.78）**；向量上 p8-9 从 0.765 升到 **0.807**（查询里带上了报表自己的用词）。

**顺带把下面那节的 RRF 毛病也修好了**：那条无关的 p237 原本靠「向量#5 + BM25#6」
的共识挤到第 1，扩词之后两路都去认真正相关的块了，它直接掉出前 6。
说明**那个排名问题的根因是「两路都在瞎猜」，而不是 RRF 公式本身**。

生成侧还多暴露了一个口径问题：扩词后 p38 也进了材料，答案里同时出现
**1.83%**（p8-9/p15）和 **1.87%**（p38，本公司口径）——招商银行「本行」与
「本集团」两个口径的披露值不同。模型如实并列了两者并提示「请按所需口径取用」，
没有擅自合并，这个表现是对的。

> **改词典后必须重建 BM25 载荷**：文档侧分词结果是建索引时固化在
> `bm25_tokens.jsonl` 里的，只往 `jieba_userdict.txt` 加词、不重建的话，
> 查询侧切出来的新词在文档侧没有对应 token，BM25 反而更匹配不上。
> 为此给 `build_index.py` 加了 `--tokens-only`（只重写分词载荷，不重算向量，约 6 秒）：
>
> ```bash
> .venv/Scripts/python.exe build_index.py --tokens-only
> ```

### RRF 会把「两路都中等」的块排到「单路最强」的块前面

这是 RRF 的固有代价，本项目实测到了。问「招商银行 2026 年上半年净息差」，
融合后的第 1 条是 `600036_0233`（财务报告 p237）——一张**债券发行/股息**表，
跟净息差毫无关系；而真正含「净利息收益率 1.83%、净利差 1.77%」的
`600036_0013`（管理层讨论与分析 p15-16）只排到**第 6**。

原因在两条路的分数里写得很清楚：

| 块 | 向量名次 | BM25 名次 | RRF |
|---|---|---|---|
| `600036_0233`（无关，p237） | #5 | #6 | 1/65 + 1/66 = **0.03054** |
| `600036_0013`（相关，p15-16） | #3 | **未进 top-10** | 1/63 = **0.01587** |

`0013` 是张大表，向量能排到第 3，但 BM25 因为 `b=0.75` 的长度归一化把它压出了
top-10。于是它只拿到**一路**的分，而「两路都中等」的块拿两路的分，反而赢了。

试过调 `K` 想把它救回来，结论是**调不动**——扫了 K=1/3/5/10/20/60/200：

```
   K  top1            目标 p15-16 名次   无关 p237 名次
   1  600036_0006                6                5
   3  600036_0006                6                3
   5  600036_0233                6                1
  60  600036_0233                6                1
 200  600036_0233                6                1
```

`0013` 的名次**全程钉在 6**：因为它只出现在一路的候选里，K 再小也改变不了
「一路得分 vs 两路得分」这个结构。K 只影响两个榜内块的相对顺序
（K=1/3 时 top1 换成了同样相关的 `0006`，p8-9）。

**影响可控**：取 6 条时 `0013` 刚好卡在第 6 名进了材料，所以最终答案的
出处（`招商银行 · 公司简介与主要财务指标 · p8-9`）是对的；但**把 `top` 调到 5
就会把它挤出去**。

**已被同义词扩展顺带修好**（见上一节）：扩词后 BM25 能认 p8-9 / p15-16 了，
两路不再「都在瞎猜」，p237 掉出前 6，`0013` 升到第 2。所以这个毛病的根因不是
RRF 公式，而是**两路都答不到点上时，共识就变成了噪声的共识**。
真要在通用场景下防这一手，方向仍然是给单路头名保名额、或改用分数归一化后
加权融合（余弦相似度与 BM25 分数先各自 min-max 归一化），本轮未做。

## 失败案例：跨公司全景题，单块检索答不了

自检第二问「**2026 年上半年哪几家银行的营业收入同比增速最高？**」是道
**跨 12 家公司的排序题**，而我们的检索单元是「单个块」——不管怎么融合，
召回的 6 个块都只是 12 家里某几家的财务指标页，**没有任何一个块包含
「哪几家最高」这个比较结果**。

这一问的召回结果倒是能看出全局检索在工作（6 条来自 6 家不同银行：
中国银行、兴业银行、农业银行、交通银行、工商银行、建设银行），
但那是「各家都被捞上来一条」，不等于「比出了高低」。

**结论**：这是**检索粒度与问题粒度不匹配**导致的失败，不是排序没调好。
要答这类题得先把每家的营业收入增速抽成结构化字段再比较（多跳 / 聚合检索），
属于本项目范围之外。如实记录，不做特殊处理。

**实际表现是「优雅地答不了」**：模型没有硬凑，而是逐家列出材料里有的数字
（中国银行营收 3,569.03 亿元、同比 +8.48%；农业银行 410,871 百万元、+11.1%），
明确指出工商银行/建设银行/交通银行的块里**只有金额没有增速**，
并说明「还缺其余 6 家的数据」——这正是要求里「证据不足就明说」想要的行为。
换句话说：**失败在检索层的粒度，没失败在生成层的诚实度**。

## 未纳入版本控制

`.env`、`files/`、`.venv/`、`extract/`、`chunks.jsonl`、`index/`、`.hf_cache/`
见 `.gitignore`。不入库的都是体积大且可由脚本完整复现的：`files/` 靠
`download_reports.py --all`，`extract/` 与 `chunks.jsonl` 靠 `extract_chunks.py`，
`index/` 靠 `build_index.py`。入库的是**无法自动重算的结论与产物清单**——
`manifest.json`（便于核对语料一致性）和 `extraction_report.md`（质检结论）。

`.env.example` 是**故意入库**的（`.gitignore` 里用 `!.env.example` 开后门）：
它只含占位符，用来告诉别人要配哪几个变量；真 key 写在 `.env` 里，不入库。
